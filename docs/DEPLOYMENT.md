# Deployment Guide

**See also:** [PROJECT_STRUCTURE_GUIDE.md](../PROJECT_STRUCTURE_GUIDE.md) for codebase organisation and [CODEBASE_QUALITY.md](../CODEBASE_QUALITY.md) for code standards.

This guide covers everything needed to prepare, build, and deploy THEIA to a production environment. Each section follows naturally from the previous, so the guide can be read top to bottom or used as a reference for specific steps.

---

## Pre-Deployment Checklist

Before any deployment is initiated, the following conditions are expected to be met. These checks reduce the risk of a failed or insecure release.

- [ ] All tests passing: `npm test`
- [ ] No console errors in the dev build
- [ ] `.env` is NOT staged (verified with `git status`)
- [ ] Environment variables are configured correctly
- [ ] Security audit has been passed
- [ ] Performance benchmarks are met (under 2 seconds load time)

Once all items above are confirmed, the environment variables can be configured as described in the next section.

---

## Environment Variables

The variables below are required for deployment. They are set through the CI/CD pipeline or directly on the server. They are never committed to the repository.

```env
VITE_REGION=your-region
VITE_PROJECT=your-project-id

# Use ONE of the following:
VITE_AGENT_ID=your-agent-id              # For single-agent mode
VITE_WORKFORCE_ID=your-workforce-id      # For multi-agent MARAG mode (recommended)
```

**Configuration notes:**

- `VITE_WORKFORCE_ID` is the recommended option. It enables the full MARAG system, where all five specialist agents (TIRA, RCRA, HPRA, ERRA, BARA) operate together.
- `VITE_AGENT_ID` is an alternative for single-agent deployments only.
- Only one of these two variables is to be provided, not both.

**The `.env` file must never be committed to the repository.** The `.env.example` file is provided as a safe template for reference.

With the variables in place, the build process can begin.

---

## Build Process

The commands below are run in order from the project root directory.

```bash
# Install all dependencies
npm install

# Build for production
npm run build
# Output is written to the dist/ directory

# Preview the production build locally before deploying
npm run preview
```

The `dist/` folder generated by the build step is the artefact that is deployed. How that folder is served depends on the deployment option selected, as described below.

---

## Deployment Options

Three deployment approaches are supported. The static hosting option is recommended for most cases.

### Option 1: Static Hosting (Recommended)

THEIA is well suited to static hosting platforms. Suitable platforms include Vercel, Netlify, and GitHub Pages.

The deployment process follows these steps:

1. Push the latest code to the main branch.
2. The CI/CD pipeline is triggered and runs the build automatically.
3. The `dist/` folder is deployed by the platform.
4. Environment variables are configured in the hosting dashboard.

This option requires no server management and is the simplest path to production.

### Option 2: Docker Containerisation

For teams that prefer a containerised deployment, the following `Dockerfile` is provided as a starting point.

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build
EXPOSE 3000
CMD ["npm", "run", "preview"]
```

### Option 3: Traditional Server (Node.js)

Where a traditional server environment is used, PM2 is recommended for process management.

```bash
# Install PM2 globally
npm install -g pm2

# Build the application
npm run build

# Start the production server with PM2
pm2 start "npm run preview" --name theia
```

Each option above results in the same production output from `dist/`. The next section describes how that output can be optimised for performance.

## Performance Optimisation

The following measures are applied to improve load times and reliability in production.

- **Code splitting** is handled automatically by Vite during the build.
- **Asset compression** is enabled on production servers using gzip.
- **Caching** is configured with long-lived cache headers on all assets in the `dist/` directory.
- **CDN distribution** is recommended by deploying the `dist/` folder to a content delivery network for global reach.

After deployment, ongoing performance is monitored as outlined in the following section.

---

## Monitoring Post-Deployment

The following areas are monitored after each deployment to confirm the system is operating correctly.

- Error logs in the browser console
- Real-time dashboard performance
- API connectivity to the fraud analysis backend
- Latency in streaming data updates
- Audit log ingestion

If any issue is detected that requires a rollback, the procedure is described below.

---

## Rollback Procedure

Where a deployment needs to be reversed, the steps below are followed in order.

1. Revert to the previous commit: `git revert <commit-hash>`
2. Rebuild the application: `npm run build`
3. Redeploy the `dist/` folder using the original deployment option
4. Verify that the application is functioning as expected
5. Document the incident in the audit logs

---

## Database and State Management

State and data are managed as follows across the application.

- User authentication state is stored locally through Preact Signals.
- Fraud case data is persisted through the backend API.
- Session data is synchronised via `signals/storage.ts`.
- No application state is stored in the Git history.

---

## Security in Production

The following security measures are active in all production deployments.

- HTTPS is enforced across all connections.
- Content Security Policy (CSP) headers are configured.
- CORS is restricted to authorised origins.
- Rate limiting is applied on all API endpoints.
- Audit logging is active for every user action.

---

## Versioning

Releases follow semantic versioning in the format `MAJOR.MINOR.PATCH`.

- Tags are created for each release: `git tag -a v1.0.0 -m "Release 1.0.0"`
- Breaking changes are documented in the release notes.

---

## Maintenance Windows

Scheduled maintenance is planned and communicated as follows.

- Windows are scheduled during low-traffic periods.
- Users are notified at least 24 hours in advance.
- Estimated downtime is between 15 and 30 minutes per window.
- A rollback plan is prepared before every maintenance window begins.
